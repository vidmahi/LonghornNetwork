2. Technical Implementation
2.1 Core Data Structures
Student Graph (Adjacency List)
Choice Rationale: Adjacency lists are optimal for sparse graphs where not all students are connected.
Space Complexity: O(V + E) where V = students, E = edges

Test Case 1: 6 students, 5 edges → ~11 storage units
More efficient than adjacency matrix O(V²) which would require 36 units

Advantages:

Fast neighbor lookup O(degree(v))
Memory efficient for sparse graphs
Easy to add/remove edges
Natural fit for graph traversal algorithms

Priority Queues
Used in both Dijkstra's and Prim's algorithms for efficient minimum extraction.
Implementation: Java's built-in PriorityQueue with custom comparators
Time Complexity: O(log n) for insert/extract operations

2.3 Connection Strength Calculation
Formula:
strength = 0
if (roommates)           strength += 4
for each (shared intern) strength += 3
if (same major)          strength += 2
if (same age)            strength += 1
Rationale for Weights:

Roommates (+4): Strongest indicator of compatibility
Shared Internships (+3): Career interests align
Same Major (+2): Academic commonality
Same Age (+1): Social proximity

Examples from Test Case 1:
Alice - Bob: Same major (2) + Shared Google (3) = 5
Dana - Evan: Same age (1) + Same major (2) + Shared Pfizer (3) = 6
Alice - Charlie: Same age (1) = 1
Frank - Others: No shared attributes = 0 (no edge)
Design Decision: Zero connection strength results in no edge. This creates:

Disconnected components (realistic for large networks)
Isolated nodes (students with no commonalities)
Efficient graph representation

5. Design Decisions and Trade-offs
5.1 Graph Representation
Decision: Adjacency List vs. Adjacency Matrix
Chosen: Adjacency List
Reasoning:

Student graphs are sparse (not all students connected)
Average degree << total students
Memory: O(V + E) vs O(V²)
Neighbor lookup: O(degree) vs O(V)

Trade-off: Edge existence check is O(degree) instead of O(1)

Acceptable since we iterate neighbors more than checking existence


5.2 Weight Inversion for Dijkstra's
Problem: Dijkstra finds shortest path, but we want strongest connections.
Solutions Considered:

Modify Dijkstra's to find longest path (requires negation, risks negative cycles)
Invert weights (10 - weight)
Use separate algorithm (Bellman-Ford)

Chosen: Weight Inversion (Option 2)
Reasoning:

Maintains Dijkstra's efficiency O((V+E) log V)
No negative weights (avoids negative cycle issues)
Simple and clear implementation
MAX_CONNECTION_STRENGTH = 10 provides sufficient range

Trade-off: Requires assumption of maximum connection strength.

Acceptable since our formula caps at ~13 (4+3+3+3+2+1 if all factors apply)


5.3 Thread Safety Approach
Decision: Synchronized Methods vs. Concurrent Collections
Chosen: Synchronized Methods
Reasoning:

Simpler to implement and understand
Operations are atomic (add friend, add message)
Performance impact minimal (small number of threads)

Trade-off: Coarse-grained locking (entire method locked)

Could use fine-grained locking (ReentrantLock) for better concurrency
Not necessary for current scale


5.4 GUI Framework
Decision: Swing

Required by project specification
Built into Java (no external dependencies)
Easier with past examples, well-documented
Sufficient for project requirements
